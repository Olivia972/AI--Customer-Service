## 设计思路

### 思路一：最值得记录的不是"搭了一个知识库"，而是"设定了边界和规矩"

智能体能直接答什么、必须核实什么、什么时候闭嘴转人工、什么情况下不许关单——这些决定来自对平台业务流程和责任划分的理解，属于业务理解范畴，技术配置只负责让规则可执行。自动解决率不是唯一目标，"答得对、不越权、不误报、该转就转"同样重要。

### 思路二：客服系统承载的是一部分的用户运营工作，不是问答机器

> 做客服知识库的时候，很多人的第一反应是把知识覆盖到足够细致、全面，或者把问题不断细分，或者干脆按流程简单区分。
>
> 但项目真正运营起来之后发现：**客服系统承载的其实是最早期的用户运营，以及产品推广迭代的任务。**
>
> 所以我们做的时候，考虑的不只是"覆盖得够不够全"，而是**用户运营场景、以及用户问题背后的需求，有没有被覆盖到、能不能被识别出来**。对不同类型的用户、处于不同产品使用阶段的用户，本来就该有不同的运营策略。

这段话是整个项目的立意起点，也解释了为什么本作品集里会出现那两个看起来"反直觉"的决策：

| 设计判断 | 落在本项目哪里 |
|---|---|
| 不能只按问题表面分类，要按**用户阶段与背后需求**分层 | → [04 与运营的结合](docs/04_与运营的结合.md)：角色分层 × 问题风险分层 × 客户状态分层 |
| **首次 / 新用户**的核心需求是信任，不是答案 | → [06 案例 A](docs/06_流程优化案例.md)：改判转人工，注册转化率约 20% → 30% |
| **投后阶段**用户的负面反馈关系到留存，必须承接情绪并给下一步 | → [06 案例 B](docs/06_流程优化案例.md)：从统一话术改为分层归因，人工跟进约 40% 完成二次下单 |
| 客服数据是**产品迭代的输入**（共性问题、转人工原因分布 = 痛点地图） | → [04 第三节](docs/04_与运营的结合.md)：AI 客服数据反哺运营决策 |

**换句话说：如果只按"覆盖全面"的思路做，会得到一套很好的 FAQ 检索系统；按"用户运营场景"的思路做，才会得到一套能影响注册转化和留存的客服系统。**
